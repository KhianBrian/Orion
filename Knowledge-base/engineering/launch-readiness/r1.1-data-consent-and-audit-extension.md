# R1.1 — Data, Consent, and Audit Extension

**Status:** Planning completed 8 September 2026 — implementation not started; synthetic-only
preparation is permitted, and every owner/clinical/DPO/vendor gate below remains open.

## 1. Outcome and scope

R1.1 defines the provider-neutral data, authorization, audit, and timing contracts that later R1 work
must implement for:

- adult eligibility and a gated minor/guardian-consent pathway;
- payment-authorised booking with a `payment_pending` appointment;
- patient-created in-app support tickets and an administrative queue;
- the server-authoritative 15/45/15 appointment and note timeline; and
- least-privilege RLS, protected-function, event, privacy, and verification boundaries for all of the
  above.

The intended dependency flow is:

```text
Patient eligibility and approved consent state
  -> one server booking command reserves a slot and creates payment_pending
  -> server creates provider checkout
  -> verified provider event changes the same appointment to booked
  -> only booked admits the assigned patient and psychiatrist
  -> scheduled end opens the 15-minute note-writing window
  -> psychiatrist release remains a separate manual action
```

This is a Tier 2-style implementation plan, not as-built evidence. It consumes the 8 September owner
amendment and the current synthetic database/application as verified below. Completing this document
does not close Phase 0–6, approve a provider, authorise real data, or make any R1 feature launch-ready.
That boundary comes from [R1.0](r1.0-governance-and-change-control.md), the
[R1 index](README.md), and the [phase planning contract](../phases/README.md#prompt-contract-for-planning).

## 5. Confirmed decisions

The following are implementation invariants, not options:

1. **Confirmed — eligibility:** An adult aged 18 or over may self-register. A minor follows a
   guardian-consent path and cannot book or join unless the approved process has moved the patient to
   an eligible state. Submission alone never activates the minor.
2. **Confirmed — booking:** The selected slot is locked server-side, one appointment ID is created in
   `payment_pending`, and only a provider result verified by Orion changes that appointment to
   `booked`.
3. **Confirmed — identity derivation:** Patient and psychiatrist IDs come from the authenticated
   caller and locked slot/appointment. The browser never supplies trusted relationship IDs, amount,
   currency, payment state, consent state, or role.
4. **Confirmed — payment privacy:** Store no card, wallet, credential, secret, or raw sensitive
   provider payload. A browser return is informational and has no state-transition authority.
5. **Confirmed — tickets:** A patient can submit and view their own in-app tickets; an authorised
   administrative queue exists. There are no uploads or email notifications. Tickets are not for
   notes, diagnosis, care history, emergencies, or treatment advice.
6. **Confirmed — time:** Database/server time is authoritative. Patient admission is
   `[starts_at - 15 minutes, ends_at)`. The scheduled consultation is 45 minutes. The note-writing
   display window is `[ends_at, ends_at + 15 minutes)`.
7. **Confirmed — notes:** The 15-minute window neither completes an appointment nor locks or releases
   a note. Only the psychiatrist manually releases a note.
8. **Confirmed — access:** No guardian access, unapproved ticket/payment write, admin clinical-note
   access, or unauthenticated data access is inferred. Every expansion needs recorded authority.
9. **Confirmed — environments:** All R1 development and tests stay synthetic until every launch gate
   closes. JaaS remains confined to D5 synthetic evidence.
10. **Confirmed — capacity:** Approximately 50 initial users is a planning forecast, not a patient
    registration cap. R1.1 adds no capacity-gate field or waitlist state.

## 7. Data model proposal

All names in this section are logical working names. Final timestamped migration filenames are chosen
only when implementation begins. Provider-specific column names and values must be mapped in R1.3
after official PayMaya material is available.

### 7.1 Cross-cutting design rules

- **Proposed for planning — current state plus immutable evidence.** Use a small current-state record
  only where booking/admission needs a fast decision; retain every consent, payment-provider, ticket
  status, and privileged change as an append-only domain/audit event.
- **Proposed for planning — function-only sensitive access.** Guardian evidence, payment events,
  ticket content, session notes, and audit rows receive no direct application-table write. Reads that
  must themselves be audited also use protected functions, because RLS cannot audit a `select`.
- **Confirmed — no client authority.** The service verifies Auth, reads server-held role, derives
  relationships from foreign keys, uses database time, and emits a correlation ID across domain and
  audit records.
- **Proposed for planning — constrained codes.** Use typed/check-constrained status, event, reason,
  and category codes. Do not accept arbitrary text into audit or operational metadata.
- **Confirmed — field accountability.** Every implemented field must carry purpose, accountable
  owner, readers, retention, disposal, and DPO/legal approval in the data dictionary. The proposal
  tables below deliberately mark retention/disposal as blocked rather than inventing a value.

### 7.2 Patient eligibility

**Proposed for planning:** Add one `patient_eligibility` row per patient as the only booking/admission
eligibility source. This is separate from `profiles.role`: a person can be a patient account while
still not eligible to book. R1.2 owns the transition rules.

For every field in this group, the accountable business data owner is the product owner, with
clinical ownership of eligibility rules and DPO/legal approval of collection and use. Those people
are not yet named. Retention clock/period and disposal are blocked under Q11 for every row; “no delete
path” below is a temporary safety boundary, not a retention decision.

| Field | Purpose/source | Readers | Retention/disposal and approval |
| --- | --- | --- | --- |
| `patient_id` | Immutable FK to the patient profile; server-derived. Accountable owners: product/DPO. | Patient-safe projection, protected booking/admission functions, approved reviewer only. | Blocked — Q11/DPO; no delete path. |
| `pathway_code` | Distinguishes adult self-registration from minor consent without storing clinical detail. | Own patient safe projection; protected eligibility functions. | Blocked — Q11/DPO; DPO approves whether this is retained. |
| `status_code` | `pending`, `eligible`, or `ineligible`; sole server booking/admission gate. | Own patient, protected booking/admission; assigned clinician may receive only a yes/no admission result. | Blocked — Q11/DPO; no client mutation. |
| `decision_reason_code` | Approved non-clinical code explaining a denied/pending transition; never free text. | Reviewer/admin function and audit reviewers; patient visibility requires owner/DPO decision. | Blocked — Q11/DPO. |
| `decided_by` | Authenticated reviewer identity when a human decision is required. | Approved reviewer/audit only. | Blocked — reviewer policy and Q11/DPO. |
| `decided_at` | Database time of the effective decision. | Same as status, with reviewer detail removed from patient projection. | Blocked — Q11/DPO. |
| `created_at` | Database creation time. | Protected functions/audit reviewers. | Blocked — Q11/DPO. |
| `updated_at` | Database time of current-state change; each change also has immutable audit evidence. | Protected functions/audit reviewers. | Blocked — Q11/DPO. |

**Confirmed:** `pending` and `ineligible` both deny booking and meeting admission. A minor consent
submission does not write `eligible`; only the later approved review/acceptance operation can do so.
An adult cannot change `pathway_code`, `status_code`, reviewer fields, or their role from the browser.

**Blocked — clinical lead required:** minimum age and suitability/refusal transitions.

**Blocked — DPO/legal required:** whether age is represented by a declaration, age band, date of
birth, or another value. R1.1 does not add a date-of-birth field by assumption.

### 7.3 Guardian/minor consent evidence

**Proposed for planning:** Use a `guardian_consent_cases` current record and append-only
`guardian_consent_events`. The case binds evidence to exactly one patient; the events prove submission,
review, acceptance/rejection, withdrawal/correction if later approved, document version, actor, and
time. No event is overwritten.

For every field in these two groups, the accountable business data owner is the company-appointed
consent owner, the clinical lead owns clinical eligibility content, and DPO/legal approves purpose,
readers, retention, and disposal. None is yet named. Q11 blocks the retention clock/period and disposal
method for every row.

| `status_code` | Current `awaiting_submission`, `pending_review`, `accepted`, or `rejected` concept; final code list depends on policy. | Patient sees a plain status; reviewer sees case status; others denied. | Blocked — owner/clinical/DPO approval and Q11. |
| `created_at` | Database case-creation time. | Protected functions/reviewer. | Blocked — Q11/DPO. |
| `updated_at` | Database time of current-state change; never a substitute for event evidence. | Protected functions/reviewer/audit. | Blocked — Q11/DPO. |

| Field | Purpose/source | Readers | Retention/disposal and approval |
| --- | --- | --- | --- |

| `case_id` | Immutable link to one consent case/patient. | Protected readers only. | Blocked — Q11/DPO. |

**Blocked — owner and DPO/legal decision required:** choose either an authenticated guardian account
or a bounded consent-submission channel. Both must satisfy the same invariants: a scoped, expiring,
single-case capability; server linkage to one patient; rate limiting; no role self-assignment; no
appointment/payment/profile/note visibility; replay prevention; and immutable evidence. An
unauthenticated general-purpose table insert is not an acceptable bounded channel.

**Confirmed deny behavior:** absent, pending, rejected, superseded/unaccepted, or unreviewed evidence
keeps the patient non-bookable and unable to join. Psychiatrists and admin support receive no guardian
identity, relationship, document, or review data. Admin access is not assumed to equal reviewer
authority.

### 7.4 Payment-authorised booking and slot reservation

**Proposed for planning — no standalone persisted hold:** Use the existing database row lock first,
then atomically create the `payment_pending` appointment and mark the slot `reserved`. The appointment
is the durable reservation and payment correlation anchor. A separate `held` object adds another
expiry/state machine without a confirmed need. Reconsider only if official PayMaya checkout behavior
requires provider work before an appointment ID can exist.

Additive appointment/slot changes:

- add `payment_pending` to `appointment_status`;
- add `reserved` to `slot_status`;
- add an immutable `booking_authorization_basis` such as `synthetic_demo` or `verified_payment`, so
  historical D1–D7 booked rows are not falsely represented as paid;
- replace the booked-only one-active-per-slot and overlap rules with forward constraints covering
  both `payment_pending` and `booked`;
- keep existing booked synthetic rows and their JaaS-only `video_room_id`; do not backfill fake
  payments; and
- add `reservation_expires_at` only after the owner approves an expiry policy. No job may infer one.

**Proposed for planning:** Add mutable-current `payment_attempts` plus append-only `payment_events`.
The attempt represents Orion's checkout/reconciliation unit. Provider callbacks never overwrite
history; each verified or rejected callback produces an event, then an idempotent protected
transition updates the current attempt/appointment state.

For every field in these two groups, the accountable business data owner is the company-appointed
payments/finance or operations owner, with DPO/legal approval of purpose, readers, retention, and
disposal. Those owners are not yet named. Q11 and the provider/commercial decisions block each
retention clock/period and disposal method.

## 9. Server/API/event contract plan

### 9.1 Eligibility and consent

1. R1.2 registration creates the patient profile and `patient_eligibility` atomically or compensates
   by leaving the eligibility state safely `pending`.
2. Adult and minor pathway selection is server-validated against the approved representation. The
   browser cannot set `eligible`.
3. If a guardian flow is approved, the server issues a scoped, expiring, single-case capability or
   requires the approved guardian account. It never exposes a general guardian role claim.
4. Consent submission appends an event and leaves the case/patient pending.
5. The approved reviewer function re-checks authority, locks the case, appends accept/reject evidence,
   updates current eligibility in the same transaction, and writes a safe audit event.
6. Booking and meeting-admission functions call one database eligibility predicate. No caller may
   bypass it by invoking a lower-level function.

Stable safe responses should disclose only `eligibility_pending`, `eligibility_not_met`, or another
owner-approved generic code. They must not disclose guardian relationship or reviewer details.

### 9.2 One payment-authorised booking command

The existing `book-appointment` route remains the single patient booking entry point; its contract is
changed in a controlled rollout rather than adding a second UI/API path.

1. Accept only `slotId` and a syntactically valid patient-scoped idempotency key. Authenticate the
   caller. Do not accept patient ID, psychiatrist ID, amount, currency, appointment status, or payment
   result.
2. In one database transaction: verify role/email/eligibility prerequisites, lock the slot, re-check
   open/future/active psychiatrist state using database time, derive psychiatrist/times, create one
   `payment_pending` appointment, set the slot `reserved`, create one payment attempt with server
   amount/currency/configuration, and write audit evidence.
3. Return the existing appointment/attempt for an identical idempotency retry. A different request
   for the reserved slot receives generic `slot_unavailable`.
4. Outside the database transaction, the server adapter creates PayMaya checkout using the Orion
   appointment/attempt references. It writes only allow-listed provider IDs/status/times. If the
   provider call fails, the attempt remains safely non-paid and the appointment remains non-booked;
   release/expiry action is blocked on policy.
5. Return only the provider-approved redirect target and Orion IDs/status required by the client.
   Never place patient, psychiatrist, clinical, or credential data in the URL.

The old service-only `book_appointment_for_patient` must not remain callable as a real-environment
shortcut that creates `booked`. During rollout it is either replaced by the new transaction or
strictly confined to an unmistakable synthetic-demo configuration. Production failure disables new
booking; it never falls back to direct booking.

### 9.3 Webhook/event processing

1. Receive the raw request only in the server function memory needed for official authenticity
   verification. Redact it from logs/errors/traces.
2. Validate method, size, content type, signature/authenticity, timestamp/replay window, and required
   provider identifiers exactly as official material specifies. These details are blocked until that
   material exists.
3. Resolve the attempt by server-stored provider reference, never by browser-return parameters or
   client-supplied Orion relationship IDs.
4. Insert one append-only `payment_event` under a unique provider/event key. A duplicate returns the
   original safe result and causes no second transition, checkout, or audit mutation.
5. In a locked transaction, compare the normalized event with current attempt/appointment state.
   Only an approved verified-success event may change `payment_pending` to `booked` and `reserved`
   slot to `booked`. Write the payment and appointment audit events with one correlation ID.
6. Failed, cancelled, out-of-order, late-after-expiry, conflicting, or unrecognized events remain
   recorded safely and do not invent a business outcome. Route them to the future approved
   reconciliation state/process.

### 9.4 Browser return and status polling

- The return route displays `checking`, `payment pending`, `booked`, or a safe unresolved/error state
  obtained from Orion's authenticated status endpoint.
- Return query parameters are treated as display hints only and are never written to payment or
  appointment state.
- Refresh/retry reads the same attempt/appointment; it never creates another checkout automatically.
- A timeout in the browser does not mean payment failure. The UI points to support only after the
  owner-approved support wording and flow exist.

### 9.5 Manual reconciliation

Manual reconciliation is a protected, admin/operations function only after owners decide who holds
it and PayMaya defines the source of truth. It requires a reason code, correlation ID, source
reference, named actor, dual review if owners require it, and immutable audit. It must never let an
operator edit patient/psychiatrist links, paste sensitive payloads, or mark paid without approved
evidence.

### 9.6 Ticket commands

- `create ticket`: authenticated patient only; derives patient ID; validates approved category,
  body length/format, rate limit, and non-upload boundary; writes ticket/message/audit atomically.
- `list/read own`: audited function returning only the caller's tickets and approved message fields.
- `admin queue/read`: audited function returning only the minimum queue metadata, then content for a
  selected ticket. It grants no appointment/payment/note access.
- `reply/status/close/reopen/escalate`: do not implement until the owner records actors and allowed
  transitions. Each eventual command locks the ticket, checks current state, appends content/event as
  applicable, changes status, and audits without copying body text.

## 12. Audit, observability, and privacy rules

### 12.1 Required audit events

| Domain | Events | Safe facts only |
| --- | --- | --- |
| Eligibility/guardian | case created, consent submitted, review accepted/rejected, eligibility transition, denied transition | Actor/subject/case/patient IDs, document version/hash, from/to code, outcome/reason, correlation, database time; no wording or identity documents. |
| Payment | reservation/attempt created, checkout reference recorded, provider event received/duplicate/verified/rejected, appointment confirmed/denied, reconciliation requested/applied/denied | Appointment/attempt/event IDs, provider-safe reference or digest if approved, normalized statuses, amount/currency if DPO approves, outcome/reason, correlation, time; no raw payload/card/wallet/credentials. |
| Ticket | created, read, reply appended, status changed, close/reopen/escalate attempted, denied access | Ticket/message IDs, actor role/ID, from/to code, outcome/reason, correlation, time; never category/body copied into audit. |
| Notes/timing | note created/read/released/amended, meeting admission granted/denied, early-end fact if later approved | Appointment/note/actor IDs, outcome/reason, correlation, server time; never note text, meeting URL, room/provider credential. |

Application actors cannot update or delete audit events. Domain functions write the domain change and
audit evidence in one transaction where possible. A provider request that cannot start a transaction
still gets a safe receipt/denial event after authentication and redaction. Audit retention, readers,
export, periodic review, and disposal remain blocked under Q11 and operations/DPO ownership.

### 12.2 Observability

- Metrics count state codes and latency without patient, guardian, ticket, appointment, provider
  reference, room, or payment identifiers unless an approved high-cardinality diagnostic store
  exists. None is approved now.
- Logs contain correlation ID, route/function code, coarse outcome/reason code, and duration only.
- Errors returned to clients are stable and generic. Provider/internal error bodies are neither
  forwarded nor copied to toasts.
- Redaction tests cover request bodies, headers, URLs, exception messages, console output, Supabase
  function logs, Playwright artifacts, screenshots/video/traces, fixtures, and analytics.
- Rate-limit counters use the minimum pseudonymous key and an owner/DPO-approved window/retention.
- No clinical-content search, ticket-body analytics, raw webhook replay store, or session recording is
  introduced.

### 12.3 Retention, consent, export, and deletion boundary

**Planning can proceed:** table relationships, constrained status/event codes, append-only evidence,
deny-first RLS, protected functions, synthetic fixtures, redaction tests, and unseeded document-version
references.

**Blocked — DPO/legal/owner required:** retention duration and clock, deletion/anonymisation,
withdrawal effect, data-subject export, legal hold, backup purge, incident preservation, and disposal
for every proposed group. No background deletion or hard-delete function may be built before those
answers are recorded.

**Consent infrastructure can exist:** document version/hash fields and append-only acknowledgment/
review evidence.

**Legal/clinical documents cannot be seeded or used:** privacy, terms, telepsychiatry,
parental-consent, payment, support, optional communications, and emergency/referral wording. Real
registration, checkout, ticket support, or sessions remain disabled until applicable versions are
approved and linked.

| Ticket leakage | Search audit rows, errors, logs, analytics, URLs, storage, screenshots, traces, reports, fixtures. | No ticket body/category if prohibited, clinical content, identity, or provider secret appears. |
| Notes | Psychiatrist authors/releases; patient reads before/after release; admin support/admin/other psychiatrist reads. | Function-only rules and read audit hold; admin support/admin explicit deny. |
| Note timing | Test one millisecond before/at/after scheduled end and `end+15m` with database-controlled time. | UI boundary is derived; no automatic lock, release, outcome, or completion at either boundary. |
| Early end/late note/no-show | Exercise proposed provider early end, late authoring, no-show, correction. | Deferred until clinical/Phase 13/R1.4 decisions; no placeholder behavior accepted. |
| Audit immutability | Each application role tries select/insert/update/delete; domain events inspected. | Direct access denied; required function events exist with safe IDs/codes/correlation only. |
| Redaction | Inject synthetic sentinel strings into ticket/provider/note inputs and force errors. | Sentinels absent from every disallowed log/artifact/storage path. |
| Regression | Run current booking concurrency, cancellation DB, RLS, unit, desktop/mobile authenticated, public navigation, D5 access matrix, lint, and build checks. | All existing synthetic behavior stays green within its historical demo boundary. |

### Acceptance gate

R1.1 implementation is not accepted until:

- the final field dictionary, role/action matrix, transition diagrams, and blocked-policy decisions are
  recorded and approved by their named authorities;
- every new table has RLS/grant allow-and-deny evidence, every privileged function has execute-grant
  denial evidence, and every sensitive read/mutation has safe audit evidence;
- one payment-authorised booking path passes concurrency, retry, webhook idempotency, forged-return,
  relation-integrity, and booked-only admission tests;
- minor gating fails closed for every non-accepted state;
- ticket isolation and content-redaction tests pass;
- database-authoritative 15/45/15 boundary tests pass with no automatic outcome/note transition;
- existing D1–D7 booking/cancellation/RLS/JaaS regressions remain green; and
- an as-built audit entry records exact migrations, schemas, grants, RLS predicates, function
  signatures, event codes, test evidence, deviations, and still-open launch gates.

Passing this gate would evidence the implemented R1.1 slice only. Company-owner go/no-go and all
Phase 0–6/production gates remain separate.

   backup treatment for every note/consent/payment/ticket/audit/security-log field.
